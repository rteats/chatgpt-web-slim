# Chrome Performance trace analysis — 2026-11-07

## Scope and privacy

Aggregate-only findings from a user-provided compressed Chrome DevTools Performance trace. **Do not commit or publish the original recording:** it includes screenshots, private conversation text, conversation identifiers and network metadata.

Environment: AMD Ryzen 7 7840HS with integrated Radeon 780M, 16 GB RAM, Chromium-based browser, multiple other extensions enabled; test conversation contained fewer than 100 messages.

The trace covers about 44 seconds, including tracing initialization; it is **not** a fresh cold-start benchmark. Measurements below are from the primary renderer main thread, except where otherwise noted.

## Evidence for forced layout / scroll measurements

Repeated Layout events lasting ~70–106 ms occur while scrolling. Recorded synchronous-layout stacks include `onScrollChanged`, `measure`, and geometry APIs such as `getBoundingClientRect`, associated with ChatGPT's own async bundles. The primary observed hotspot is **main-thread script and style/layout coupling**, rather than network asset download.

The slow click at ~24.25 s included ~598 ms of microtasks (603 microtasks in one event) inside the click processing task, and nearby geometry/layout activity. This does not establish that all clicks are slow; only three interactions have nonzero IDs in this trace.

Repeated layout shifts occur while scrolling/navigation. Some `LayoutShift` events have large per-event scores, but the raw cumulative score in trace events is **not** a standard, user-facing CLS metric; many events overlap with activity and input.

## Interference from other browser extensions

At least six distinct `chrome-extension://` script prefixes appear in call stacks. One third-party extension injects jQuery 2.1.3 and a stack from that extension precedes a ~80 ms style recalculation at ~24.85 s. This proves interference is possible, **not** that any particular extension caused the main problem. Other heavy stack traces originate from chatgpt.com bundles.

There is no evidence in the extracted hot-stack URLs identifying this repository's extension as active during the measurement. Treat the recording as a baseline with other extensions enabled unless the environment is independently verified.

## Action taken

- PR #1: refactor offscreen containment to collect *all* bounding-box reads before any turn mutations, avoiding per-turn read/write interleaving that can trigger repeated forced layout.
- Make experimental containment opt-in by default until real A/B testing shows a benefit.
- Add a mock-DOM regression test asserting all geometry reads precede all CSS/DOM writes.

## Next controlled measurements

2. With other extensions disabled, capture three traces each of Web Slim off/on while scrolling the same long chat and while switching short → long → short.
3. Record a 1–2 second idle start then identical scroll distance and speed. Alternate A/B order to minimize warm-cache and thermal effects.
4. Check responsiveness, Long Tasks, Layout/UpdateLayoutTree, scroll jumps, find-in-page, keyboard navigation and accessibility. Inspect the Web Slim popup to confirm the optimizer actually marked turns: if `contained = 0`, there is no containment effect to benchmark.

## Limitations

The trace does not include a complete controlled paired comparison, so no speedup or root-cause attribution to a single library/extension is proven. CPU-profiler startup itself creates a ~1-second task and must be excluded from web-app long-task conclusions.
